Feasibility verdict — NVFP4 on A100

Target checkpoint
unsloth/gemma-4-E4B-it-NVFP4
Did NVFP4 run on A100?
NO — NVFP4 does NOT run on A100
Why it fails
The checkpoint declares architecture 'Gemma4ForConditionalGeneration' (model_type 'gemma4') with a compressed-tensors NVFP4 (4-bit) quantization_config. vLLM 0.10.2 has no support for the 'gemma4' architecture, so load fails at ModelConfig validation ('rope_scaling should have a rope_type key') before any weights or NVFP4 kernels are touched. It is NOT simply a rename of gemma-3n: the loadable bf16 model is model_type 'gemma3n' (Gemma3nForConditionalGeneration), a different architecture.
Model actually benchmarked
unsloth/gemma-3n-E4B-it (bf16)
GPU / stack
NVIDIA A100-SXM4-80GB (sm_80) · vLLM 0.10.2 · torch 2.8.0+cu128

Even if the 'gemma4' architecture were supported by vLLM, NVFP4 (FP4) uses 4-bit tensor-core / CUTLASS kernels that require Blackwell (sm_100+, e.g. B200/GB200). The A100 is sm_80 (Ampere) and has no FP4 tensor cores, so the quantized matmuls could not execute natively on this hardware regardless. FP4 on Blackwell would roughly double dense throughput and cut memory ~4x vs bf16; on A100 the practical path is bf16 (or FP8 on Hopper).

Decode is latency-bound at small k (k=1→4 adds only ~8s total; the 4th seed ~0.6s), so best-of-4 is nearly free.
